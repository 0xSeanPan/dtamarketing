# M3 被智能体采用（Adoption）

> 状态：进行中（Phase 2 第一优先；协议情报已入库，协议追踪页已上线） ｜ 最后更新：2026-11-07 ｜ 总纲：`../01-总纲/研究框架.md`

## 1. 定义

智能体在候选集中选择了你，存在两条路径：推荐路径——agent 把你作为答案的一部分推荐给委托人，由人完成最后确认；调用路径——agent 通过工具调用（MCP、API、function calling）直接使用你的服务完成事务，无需人类介入。人类营销对标是转化优化，但转化点从"落地页上的说服"前移到"agent 决策函数里的比较"。

领域现状：MCP 已成为主流工具接入生态之一；交易侧，ACP（OpenAI + Stripe，ChatGPT 内生产运行，Etsy、URBN 等已接入）与 UCP（Google + Shopify，2026 年 1 月生产）构成两大协议阵营 [2026-08][A] Stripe 官方博客（stripe.com/blog/10-lessons）[2026-08][B] 第三方文档。这意味着"被采用"正在从技术集成问题变成协议卡位问题。

## 2. 研究问题

- M3-RQ1：agent 在多个候选工具/商品间做选择时，决策变量是什么——价格、延迟、成功率、描述质量、评分、品牌先验、目录排名？权重如何估计？
- M3-RQ2：MCP 目录（官方及第三方注册表）中，什么样的 server 获得安装与调用？工具名称、描述写法、参数设计、认证摩擦的影响如何度量？
- M3-RQ3：协议化目录（ChatGPT 内电商、Google AI Mode 商品目录）的准入条件、排序逻辑、抽成结构？两大协议阵营（ACP / UCP）的覆盖差异与商家策略？
- M3-RQ4：免费增值、明码标价、按量计费在 agent 渠道的表现差异——agent 偏好可预测成本还是低价？
- M3-RQ5：推荐路径与调用路径的分流比例随任务类型（低风险 vs 高金额）如何变化？人的确认环节在哪一类交易中仍不可绕过？
- M3-RQ6：无 API 的纯内容型业务如何"被采用"？（被推荐即采用，回到 M2 的引用份额，需在此处定义边界）

## 3. 方法与实验协议（草案）

工具采用实验：构造同一能力的多个变体 MCP server（改写名称/描述/参数复杂度/定价表述），发布到目录并投放等量曝光，统计安装与调用差异。变量每次只动一个。

协议卡位追踪：按月记录 ACP、UCP、x402 及国内同类（支付宝/微信的 agent 支付动向）的商家准入、类目扩张、结算规则变化，形成协议时间线。

决策变量访谈：收集公开的 agent 产品文档、开发者日志与商家案例，提取平台声明的排序与推荐逻辑，与实验结果互证。

## 4. 指标体系

| 指标 | 定义 | 采集方式 |
|---|---|---|
| 安装转化 | 目录曝光 → MCP server 安装 | 目录后台 |
| 调用量与留存 | 日均调用、7 日留存调用方数 | 服务端日志 |
| 推荐份额 | 推荐路径中被选为首选的比例 | 面板测试（与 M2 共用） |
| 协议渗透 | 经 ACP/UCP 完成的订单占比 | 交易后台 |
| 决策因子权重 | 各变量对选择概率的边际影响 | 对照实验 |
